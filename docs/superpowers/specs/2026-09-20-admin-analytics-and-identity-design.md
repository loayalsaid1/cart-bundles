# Admin Identity, Merchant Visibility, and Proof-of-Value Analytics

Date: 2026-09-20
Status: approved for spec review
Scope: one implementation plan for identity, churn, merchant profile, revenue, queue health, and leaderboard. Conversion matcher SOLID refactor is a **separate commit** after this lands.

## Problem

The admin console can count merchants and conversions, but it cannot answer the questions that matter for an upsell app:

- Who is the admin, as a real user rather than an env password?
- Who is merchant `1305146709` (store name, email, domain)?
- When did they uninstall, and can we email them?
- How many riyals did Cart Bundles actually generate?
- Are BullMQ workers failing, or are we just counting inbound webhooks?

Secondary: embed/admin sessions expire with no recovery. Conversion matching for recommendations is heuristic-only and lives in a kind-switch that violates SRP.

## Goals

1. Admin authenticates as a `users` row with `role = admin` (email + hashed password).
2. Expired local JWT: embed calls `embedded.destroy()`; admin reloads to login.
3. Persist merchant store identity from Salla `/oauth2/user/info`.
4. Persist `uninstalledAt` from `app.uninstalled`.
5. Track extra revenue generated by matched upsell items; headline KPI is widget-attributed.
6. Replace webhook-volume vanity metric with failed-queue counts.
7. Top 5 merchants by conversions on the overview.
8. Merchant table shows name + id; row click opens a profile/analytics modal.

Non-goals for this spec:

- Dedicated `/admin/merchants/[id]` page (modal first).
- Waiting/active queue charts (failed jobs only).
- Removing category targeting from offer CRUD.
- Matcher strategy refactor (separate commit).
- Putting Salla staff accounts into `users`.

## Current state (constraints)

- NestJS backend is source of truth. Frontend Next.js rewrites `/api/*` to it. Legacy Next webhook/auth routes exist but must not gain new behavior.
- Admin login: `POST /admin/login` compares `ADMIN_PASSWORD`, mints JWT `{ merchantId: 0, userId: 0, role: 'admin' }`.
- `users` table: `id, name, email, createdAt`. Unused by auth.
- `merchants` table: tokens + `isActive` only.
- `offer_stats` / `daily_stats`: impressions, clicks, addToCart, conversions. No money.
- `OrderConversionService` matches order line products to active offers, increments conversion count, Redis-locks per `(merchant, order, offer)`.
- Storefront events buffer counters in Redis; a flush worker upserts Postgres.
- BullMQ queues: `salla-webhooks`, `app-activity`, `storefront-events`.
- Salla Easy Mode: tokens from `app.store.authorize`. User info: `GET https://accounts.salla.sa/oauth2/user/info`. Uninstall payload includes `uninstallation_date`.

## Architecture

Keep ownership in existing modules. Do not create an `AdminAnalyticsModule` facade.

```text
AuthModule            users table, admin login, JWT, seed
MerchantsModule       profile columns, user-info fetch, uninstall
WebhooksModule        authorize -> profile; uninstall -> uninstalledAt
LoggingModule         revenue stats, attribution, overview, queue health
Front-End admin       login form, KPIs, merchants table + modal, expiry
```

Each new type/service has one reason to change:

| Unit | Responsibility |
|---|---|
| `AdminAuthService` | Verify admin credentials, issue admin JWT |
| `UsersService` | Persist/lookup users. `AdminAuthController` does not talk to Drizzle |
| `MerchantProfileMapper` | Map Salla user-info JSON -> merchant columns |
| `MerchantProfileService` | Call `OAuthService.fetchUserInfo` (full payload) and persist mapped columns, fail-soft |
| `ConversionAttributor` | Given offer + recent storefront events, return `widget` or `inferred` |
| `ConversionRevenueCalculator` | Given match + order line amounts, return extra SAR |
| `QueueHealthService` | Failed job counts for the three queues |
| `AdminStatsService` | Compose overview/list/detail DTOs (already exists; extend) |
| Frontend `http.ts` | Single 401 expiry handler |

Controllers stay thin. WebhooksService stays a dispatcher.

## 1. Admin identity

### Schema

`users`:

- `passwordHash text not null` — `scrypt` via `node:crypto`, stored as `scrypt$N$r$p$saltB64$hashB64` (no bcrypt dependency)
- `role varchar(32) not null default 'admin'` (pg enum or check: `admin` only for now)
- existing `email` unique remains the login key
- `name` stays; seed uses the email local-part
- Table is unused today; migration may add `NOT NULL` columns directly. If any orphan row exists, the seed upsert covers the admin email only.

Do not reuse `ADMIN_PASSWORD` as the runtime login path. Env vars become seed inputs only:

- `ADMIN_EMAIL`
- `ADMIN_PASSWORD`

`.env.example` documents both. Remove runtime comparison in `AdminAuthController`.

### Login

`POST /admin/login` body: `{ email, password }`.

Flow:

1. Lookup user by email.
2. Reject if missing, wrong role, or hash mismatch (same 401 message).
3. Sign JWT `{ userId, role: 'admin' }`. Stop sending `merchantId: 0`.
4. `RolesGuard` already reads `user.role`. `EmbedContext` becomes:

```ts
export interface EmbedContext {
  merchantId?: number;
  userId: number;
  role?: 'admin' | 'merchant';
}
```

Merchant embed tokens continue to set `merchantId` + `userId`. Admin tokens omit `merchantId`. Merchant-scoped controllers keep requiring `user.merchantId`; they never treat a missing merchant id as `0`. Any code that assumed admin `merchantId === 0` must be updated.

Cookie `adminToken` unchanged (httpOnly, lax, 12h).

### Seed

`Back-End/scripts/seed-admin.ts` + `package.json` script `db:seed-admin`.

- Requires `ADMIN_EMAIL` and `ADMIN_PASSWORD` (min 8 chars, already in DTO).
- Upserts by email: updates hash if the row exists so password rotation is a re-seed.
- Idempotent. Never logs the password.

Frontend login form: email + password fields, i18n en/ar.

## 2. Expired token recovery

Backend already throws `UnauthorizedException('TokenExpiredError')` and clears cookies.

Frontend `lib/http.ts` is the single interceptor:

- On 401, parse body `message`.
- If `message === 'TokenExpiredError'`:
  - Path starts with `/admin` **or** current page is admin: `window.location.reload()`.
  - Else (embed): `embedded.destroy()` so Salla reloads the iframe and re-issues a SDK token.
- Other 401s stay as `ApiError` (invalid token, missing cookie).

Admin shell today treats **any** `useAdminOverview().isError` as logged-out. Change to: show login form only on 401. Network/5xx keep the shell and show error.

Embed layout already destroys on initial verify failure. Runtime API 401s currently toast "Session expired" on the products page only. Moving this into `http.ts` covers all embed API calls.

Do not loop: destroy/reload once per expiry. `http.ts` should not retry the failed request.

## 3. Merchant store identity

### Schema (`merchants`)

Nullable:

- `storeName varchar(255)`
- `storeEmail varchar(255)`
- `storeDomain varchar(255)` (merchant `username` from Salla, e.g. store slug)
- `avatar varchar(512)`
- `uninstalledAt timestamp`

### Fetch

On `app.store.authorize`, after `upsertAuthorized`:

1. Call existing `OAuthService.fetchUserInfo(accessToken)` after expanding its return type to the full `SallaUserInfoResponse` (ids stay derived from it). One HTTP client, one URL.
2. `MerchantProfileMapper` maps that payload onto merchant columns (pure function, unit-tested).
3. `MerchantProfileService.refresh(merchantId, accessToken)` updates the row.
4. Fail-soft: log + activity warn if user-info fails; tokens still persist so Salla ACK succeeds.

Salla user-info fields (from existing types + Salla OAuth docs):

- `data.merchant.id` -> already keyed
- `data.merchant.name` -> `storeName`
- `data.merchant.username` -> `storeDomain`
- `data.email` / merchant email if present -> `storeEmail`
- `data.merchant.avatar` or `data.avatar` if present -> `avatar`

Mapper accepts optional nested fields; missing keys stay null. Do not block authorize on incomplete payload.

Custom-mode `POST /salla/oauth/token` already fetches user-info for ids. After this change, persist the same profile fields there too (one code path: `MerchantProfileService.refresh(merchantId, accessToken)`).

### Backfill

`scripts/backfill-merchant-profiles.ts`:

- For each `isActive` merchant with a usable token, call user-info.
- Skip / log merchants whose refresh fails (`reauth_required`).
- Rate-limit (sequential or small concurrency) so we do not burst Salla.

## 4. Churn

Salla `app.uninstalled` payload (docs):

```json
{
  "event": "app.uninstalled",
  "merchant": 1234509876,
  "created_at": "2022-12-31 12:31:25",
  "data": {
    "uninstallation_date": "2021-10-07 12:46:07",
    "refunded": false,
    "store_type": "live"
  }
}
```

`MerchantsService.deactivate(merchantId, uninstalledAt?: Date)`:

- `isActive = false`
- `uninstalledAt = parsed uninstallation_date` or webhook `created_at` or `now()`
- invalidate caches (already)

`upsertAuthorized` on reinstall:

- `isActive = true`
- `uninstalledAt = null`

Type the uninstall event (`SallaAppUninstalledEvent`) instead of `SallaAppEventBase`.

Admin merchants page:

- Active/connected table: name + id, status, offers, created.
- Separate "Churned merchants" section: name, id, email, `uninstalledAt`.
- Filters can be two sections on the same page (no new route).

Backfill `uninstalledAt`:

- From `event_logs` where `event_name = 'app.uninstalled'` and merchant `isActive = false` and `uninstalledAt is null`.
- Use `event_data.data.uninstallation_date` or `event_date`.

- Row click opens dialog (existing shadcn dialog pattern).
- Modal: avatar, name, email, domain, status, KPIs, last activity. No nested routing.

## 6. Proof of value (revenue)

### Schema

`offer_stats` and `daily_stats` add:

- `revenueGenerated numeric(14,2) not null default 0` — all matched extra revenue
- `revenueAttributed numeric(14,2) not null default 0` — widget-attributed subset
- `conversionsAttributed bigint not null default 0` — widget-attributed conversion count

Headline admin KPI: `sum(revenueAttributed)` formatted as SAR.

Keep `conversions` as total heuristic matches (widget + inferred) so existing merchant dashboards do not silently drop numbers. Overview may show both; the marketing number is attributed.

### Order line amounts

Extend `SallaOrderItem` with optional amount fields Salla commonly sends (`amounts.total.amount`, `amounts.price.amount`, `price.amount`, `total`). Extraction is a dedicated function with a typed fallback chain. If no amount is present, revenue delta is `0` but conversion count still increments.

Currency: store SAR numeric. Ignore currency mismatches; do not convert.

### Extra revenue (not order total, not trigger product)

| Kind | Revenue lines |
|---|---|
| `product_add_on` | related product line amounts |
| `bundle` | related product line amounts (not trigger) |
| `upgrade_offer` | upgrade product line amount |
| `cart_recommendation` | related product line amounts |
| `quantity_discount` | sum of matched target product line amounts that meet min tier (cannot isolate "extra units" without original price; do not invent). If amount missing, 0 |

If multiple offers match the same line, each offer still records its own extra lines. That can double-count platform totals when two offers share a related product. Accept for v1; document it. Do not split amounts.

### Attribution tag

After a heuristic match, `ConversionAttributor` looks up recent storefront activity for `(merchantId, offerId)` with action in `offer.click`, `offer.add_to_cart` and `createdAt` within 7 days, optionally matching `metadata.productId` to a converted related product.

- Hit -> `source: 'widget'`, increment attributed counters + attributed revenue
- Miss -> `source: 'inferred'`, increment total conversions/revenue only

Activity lookup must be indexed: existing `activity_logs_merchant_created_idx` and `activity_logs_offer_idx`. Query is bounded (`limit 1`, date window). If this becomes hot, add a Redis set written by the storefront processor; not required for v1.

Activity log for `offer.conversion` metadata:

```ts
{ sallaOrderId, source, revenue, attributedRevenue }
```

### Stats pipeline

`OfferStatsService.buffer` today increments integer fields by 1. Extend:

- `buffer(merchantId, offerId, field, amount = 1)` for counts
- `bufferRevenue(merchantId, offerId, { generated, attributed })` using Redis `HINCRBYFLOAT` (add to `RedisService`; do not call ioredis from the stats service)

Flush `toDeltas` includes the new numeric fields. Postgres upsert adds them. Read-model hashes include `revenueGenerated` and `revenueAttributed`.

Admin overview cache key becomes `admin:overview:v2` (TTL 60s). Old `admin:overview` keys are ignored.

### Backfill

Revenue cannot be reconstructed from current activity logs (no amounts). Script:

- If `event_logs` still has unredacted order payloads with line amounts, optionally recompute. Redact currently strips tokens not amounts; order payloads in `event_logs` may work.
- If payloads lack amounts, skip and log "revenue starts from deploy date".
- Do not fake historical SAR.

## 7. Queue health

`QueueHealthService` injects the three BullMQ queues (LoggingModule already has activity + storefront; webhooks queue lives in WebhooksModule). To avoid a circular import, put `QueueHealthService` in `queue/` (next to `QueueModule`) and import it into LoggingModule.

For each queue, `getJobCounts()` and expose `failed`. Overview:

```ts
queueHealth: {
  webhooksFailed: number;
  activityFailed: number;
  storefrontFailed: number;
}
```

Replace `webhooksLast24h` on the overview DTO. Frontend KPI becomes "Failed jobs" (sum) or three small numbers. `systemHealth.status` is `degraded` if any failed count > 0 **or** recent error logs > 5 (keep existing error heuristic, add queues).

Do not add waiting/active charts.

## 8. Top 5 merchants

Overview query: `offer_stats` grouped by `merchantId`, `order by sum(conversions) desc limit 5`, join `merchants` for `storeName`.

```ts
  merchantId: number;
  storeName: string | null;
  conversions: number;
  revenueAttributed: string; // decimal as string
}>
```

Render a compact table on the overview under KPIs.

## 10. Conversion matcher (separate commit)

Not in the first implementation plan. Spec so the first commit does not paint us into a corner:

- First commit may add `source` and revenue **inside** the existing matcher functions without the strategy split, if that unblocks analytics. Prefer extracting calculator/attributor as pure functions even in commit 1.
- Commit 2: `ConversionMatcher` interface, one class per kind, registry. `matchesRecommendation`: `cart_related` requires trigger product **and** a related product in the order; `general` requires a related product. Organic adds without widget events stay `inferred`.
- Category targeting: matcher does **not** match `selected_categories` (order payload has no category ids; we do not fetch catalog during webhooks). Offer CRUD keeps category targeting. Document this explicitly in matcher tests.

## Performance

- Overview: existing 60s Redis cache; version the key.
- Merchant list: identity columns on the same select; no per-row Salla calls.
- User-info: once per authorize, not per dashboard request.
- Attribution query: one indexed existence check per matched offer, inside the already-serialized conversion lock.
- Queue counts: BullMQ `getJobCounts` is O(failed set); three calls per cached overview.
- Stats flush: extra hash fields, same scan worker.
- Seed/backfill: CLI, not request path.

## Error handling

- User-info failure: merchant remains active with tokens; profile null; activity `warn`.
- Hash/login: generic 401, no user enumeration beyond existing timing (optional dummy hash later; not required).
- Missing line amounts: conversion without revenue.
- Queue health Redis down: overview `systemHealth.status = degraded`, zeros, do not 500 the dashboard.
